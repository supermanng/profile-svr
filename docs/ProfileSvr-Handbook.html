PART I

Product Requirements

1 · overview

What ProfileSvr is

ProfileSvr is the identity and onboarding backbone for the Muuvly app. It owns the customer profile, the devices a customer signs in from, and every one-time-passcode ceremony that proves who is acting — while delegating credentials to the central SSO and message delivery to the Message Centre.

Goals. A new customer reaches a fully verified, transaction-ready profile in one guided flow; every sensitive change (device, PIN, password) demands proof beyond a password; every action leaves an audit trail with device and IP; and a downstream transaction service can read risk signals (tier, fresh-device gate, PIN state) from a single DTO.

Non-goals. ProfileSvr does not store passwords or mint tokens (the SSO does), does not deliver messages (the Message Centre does), and does not execute transactions — it only supplies the identity facts transactions are gated on.

One sentence: the SSO knows who you are, ProfileSvr knows everything else about you — and nothing about you changes without an OTP.

3 · functional requirements

Requirements

Onboarding

FR-1Onboarding starts with an email and a device; the service pre-allocates the identity (sourceId) that becomes both the SSO user's SourceId and the profile id.
FR-2The email is proven by a 6-digit OTP before any account exists; verify-auth then creates the SSO auth and a staging record (status: AuthCreated) and returns onboarding-typed tokens so no separate login is needed.
FR-3The phone number is proven by an OTP delivered over WhatsApp (SMS switchable by config); in the KYC path the phone comes from the BVN/NIN record, never from the client.
FR-4The profile is only created (status Active) at the final step, after both email and phone are verified and personal details are supplied.
FR-5KYC is proven biometrically: an AWS face-liveness session opens at initiate-kyc, and complete-kyc compares the liveness selfie with the BVN/NIN photo — a match marks the id verified, sets kycStatus: Approved, promotes to tier 1 and provisions the banking accounts. A failed liveness or mismatch is a soft failure the client retries with a new session.
FR-6Re-initiating before the profile exists simply resends a fresh OTP (60 s cooldown), invalidating earlier codes.

Devices

FR-7A profile may accumulate many devices over time, but exactly one is in use at any moment — and an in-use device serves exactly one profile. Released bindings are kept as history.
FR-8Devices are registered only inside OTP-protected flows (onboarding, resume, device change); there is no standalone registration endpoint.
FR-9Login refuses any device other than the active one (403); only the OTP ceremonies move a binding.
FR-10A locked-out user (new phone, no token, no profile id) switches devices with password + email OTP alone: initiate-device-change → change-device.
FR-11The active binding's linked_at opens a 24-hour reduced-limit gate (deviceRecentlyLinked) that a transaction service reads live; it expires by arithmetic, not by a job.
FR-12An SSO account with no local record (interrupted signup) resumes via its own OTP ceremony, reclaiming the original profile id from the token's SourceId claim; a device in use by another profile cannot be claimed through resume.

Credentials & PIN

FR-13Login is an SSO password grant gated on the registered active device; it returns tokens, a deviceStatus (New / Existing / Unlinked), the token type, and the full profile DTO.
FR-14Sessions refresh without a password (/auth/refresh); app relaunch rehydrates from the token alone (/auth/me).
FR-15Password change requires the current password; password reset requires an email OTP; both execute on the SSO.
FR-16The 4-digit transaction PIN is set once, changed with the current PIN, or reset via email OTP; it is stored as PBKDF2-SHA256 with a per-profile salt and is verified during transactions, not by this API.

Banking accounts & money-in

FR-25Once the identity (BVN/NIN) is verified, the service provisions the banking chain automatically: customer (CIF) → NGN account → CAD account → virtual (collection) account — each step get-or-create and best-effort, never blocking the caller.
FR-26Failed provisioning surfaces as kycStatus: ProvisioningFailed and self-heals: create-profile, login and refresh each retry the missing pieces until the chain completes.
FR-27The bank behind the accounts is replaceable: endpoints only see a facade, with the core-banking provider (OneCore today) and the virtual-account provider (VantPay today) swappable behind two interfaces.
FR-28Login and refresh return the live account list (with balances) and the latest exchange rate per currency pair; provider outages yield empty lists, never a failed login.
FR-29Incoming virtual-account credits arrive on a signed webhook, are stored idempotently by transactionRef, and a background job settles them into the CBA naira account — with configured platform and provider charges — retrying transient failures and dead-lettering permanent ones.
FR-30The credit-posting job carries a heartbeat surfaced on /health; a stalled job degrades health. A MySQL advisory lock keeps multiple replicas from double-posting.

Platform

FR-17Every response uses the {isSuccess, data, message} envelope with a human-readable message, always populated.
FR-18Every significant action writes an activity row: type, profile, device, client IP, timestamp — readable by the owner as a paged feed.
FR-19Tokens carry a type claim (onboarding · temporary · profile-active) written to the SSO; ProfileSvr re-derives it per request from the live profile status so a stale token can never cross a gate.
FR-20Onboarding-typed tokens reach only onboarding endpoints; profile-active tokens reach everything except onboarding; crossing the line is 403.
FR-21OTP emails are branded HTML (configurable brand name); WhatsApp/SMS are plain text; all sends verify the Message Centre's response body, not just the HTTP status.
FR-22Optional end-to-end payload encryption (AES-256-GCM envelope) can be switched on by config; docs and health stay plaintext.
FR-23BVN and NIN are stored raw but always masked to the last 4 digits in every API response.
FR-24Schema changes apply automatically at startup via EF Core migrations.

4 · security model

Three layers of proof

Token types

typeWhenMay reachMay not reach
temporaryToken authenticates, no profile rowresume bootstrap, /me, otp/verifyeverything else
onboardingProfile AuthCreatedinitiate-phone, initiate-kyc, create-profile (+ shared)PIN & password endpoints
profile-activeProfile Activeeverything except onboardingonboarding endpoints

The claim lives in the JWT (written to the SSO before token mint) for other services to read — but ProfileSvr always recomputes it from the database per request, so the gate flips the instant create-profile succeeds, with no stale-token window.

OTP discipline — identical everywhere

  • 6-digit cryptographically random code; public 16-character retrievalCode reference (no 0/O/1/I).
  • Stored as SHA-256(code | purpose | target) — a code can never verify outside the exact ceremony and recipient it was minted for.
  • 10-minute expiry · 60-second resend cooldown · 5 attempts then locked · one active code per purpose · superseded codes invalidated.
  • If the send fails after issuing, the orphaned code is consumed and the caller gets a 502 — no live code without a delivered message.

Everything else

  • PIN: PBKDF2-SHA256, 100k iterations, fresh random salt per set; constant-time compare.
  • Device trust: password proves the account, the mailbox OTP approves the device — stolen credentials alone cannot enroll an attacker's device.
  • Payload encryption (optional): AES-256-GCM, fresh nonce per message, authenticated — a flipped byte is rejected, never garbled.
  • Fail closed: SSO or KYC unreachable → 503 before anything persists.
  • Webhook integrity: inbound credit notifications must carry X-Signature = HMAC-SHA256 of the raw body (fixed-time compared); outbound CBA postings are signed the same way.
  • Biometric proof: tier 1 requires a live selfie matched against the BVN/NIN photo — a stolen id number alone cannot pass KYC.

6 · banking accounts

Accounts & money-in

Once KYC approves an identity, ProfileSvr turns the profile into a banked customer without any further client calls — and once the customer shares their virtual account number, incoming transfers settle into their naira account automatically.

The provisioning chain

Runs first at complete-kyc (the provider requires a verified BVN/NIN), and re-runs at create-profile, login and refresh until complete:

  • 1 · Customer (CIF) — searched by email on OneCore first, created only if absent (idempotent).
  • 2 · NGN account, then 3 · CAD account — existing accounts in the right currency are adopted; otherwise opened with the configured product codes.
  • 4 · Virtual account — a static VantPay collection account tied to the BVN/NIN, opened only after the NGN account exists so every credit has somewhere to land; its routing row (virtual → naira) is written in the same transaction.

Every step is best-effort: a provider outage logs a warning, leaves kycStatus: ProvisioningFailed ("we'll retry automatically"), and the next login or refresh picks up where it stopped. The caller's request never fails because a bank was down.

The money-in pipeline

  • Notify — the provider calls POST /webhook/virtual-account-credit; the signature is verified and the credit stored, idempotent on transactionRef (redeliveries and races are absorbed).
  • Settle — the PostCbaCreditsJob sweeps stored SUCCESSFUL credits every ~2 s (batch 1000), resolves the virtual → naira mapping, computes the platform charge (ChargePercent) and provider charge (ProviderChargePercent), and posts a signed credit to OneCore's integrations webhook.
  • Converge — a CBA "duplicate reference" reply counts as settled; transient failures retry each tick up to MaxPostAttempts; permanent (4xx) failures dead-letter immediately with the error preserved.
  • Observe — the job beats a heartbeat that /health reports; a stalled job flips health to degraded. Replicas coordinate through a MySQL advisory lock.

  • Onboarding completion: initiate → Active conversion, and time-to-Active.
  • OTP health: delivery success per channel, verify-on-first-attempt rate, lockout rate.

PART II

API Reference

8 · conventions

Read this first

Envelope. Every response, success or failure, is { "isSuccess": bool, "data": … | null, "message": string } — the message is always populated and safe to show in the UI. HTTP status codes carry the semantics.

Auth. Protected endpoints take Authorization: Bearer <accessToken>. Tokens come from verify-auth (during onboarding) or login, and refresh via /api/auth/refresh. The badge on each endpoint shows who may call it.

OTP ceremonies. Every initiate-* returns a retrievalCode; quote it back together with the 6-digit otp the user received. Codes expire in 10 minutes, lock after 5 wrong attempts, and resend is throttled to once per 60 seconds.

Payload encryption (when Encryption:Enabled): request and response bodies travel as { "data": "base64(nonce‖ciphertext‖tag)" }, AES-256-GCM with the shared key. /health, /swagger, /openapi stay plaintext.

The single verify endpoint

POST/api/otp/verify🔒 any

One endpoint verifies every plain confirmation; the section enum selects what gets confirmed. 13 · webhooks

Money in

POST/webhook/virtual-account-creditanon + HMAC

Called by the virtual-account provider when a customer's collection account is credited. When DigitVirtual:WebhookSecret is configured, the X-Signature header must be the lowercase-hex HMAC-SHA256 of the raw body (fixed-time compared); when unset (dev only), verification is skipped. The credit is stored idempotently by transactionRef — the PostCbaCreditsJob then settles it into the mapped CBA naira account, minus the configured charges. A storage failure returns 500 so the provider redelivers rather than losing the credit; a malformed payload is acknowledged and dropped (redelivery cannot fix it).

Request
{ "transactionRef": "VA-2026-000123",
  "amount": 15000.00,
  "account": "8812345678",
  "sourceAccount": "0123456789",
  "sourceBank": "GTBank",
  "senderName": "CHIDI OKafor",
  "narration": "rent",
  "transactionDate": "…",
  "status": "SUCCESSFUL" }
Response 200
{ "status": "received",
  "receivedAtUtc": "…" }
// or { "status": "ignored", … }
//    for malformed payloads

401 invalid signature · 500 storage failure — provider should redeliver

Only credits with status: SUCCESSFUL are settled. Transient posting failures retry every ~2 s up to MaxPostAttempts (default 10); permanent 4xx rejections dead-letter with the error preserved; a CBA "duplicate reference" reply counts as settled.
